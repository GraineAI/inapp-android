## 0.11.0

- **Calls connect faster.** The SDK now sets each WebRTC call up with Graine's call servers directly, with a short-lived permission it fetches ahead in the background, instead of an extra hop through Graine's web service. A call that can't use it connects exactly as before. Nothing to change in your app. In `ai.graine:inapp-android` and `ai.graine:inapp-android-rtc` 0.11.0.
- **New, optional: `GraineCalls.prepareCall(reason, variables, agent)` — the next call set up before the tap.** Call it on a screen with a call button, each time the screen appears; the tap then only dials. Pass the same reason and variables you will pass to `startCall` — anything different and the call is set up at the tap, as before. Nothing is dialled, recorded or billed before the tap: the microphone stays off until the user taps Call. The prepared call is let go when the app goes to the background, when the signed-in user, their memory choice or their time zone changes, after 4 minutes, or when a call rings.
- **Every call reports how it connected**, shown in Execution Logs: WebRTC or the standard connection (and why), whether it was set up ahead, the time from the tap to the agent's first words, and the call's audio quality. Timings only — nothing personal. Nothing to change in your app.

## 0.10.3

- **A stalled WebRTC dial is redialled after half a second, not 3 seconds.** A dial the server has acknowledged is answered within a few dozen milliseconds; one still unanswered half a second after that is cancelled and made once more on a fresh connection, and a second stalled dial continues on the standard connection, with `transportFallbackReason` `no_answer`. 0.10.2's 3 seconds only delayed that fallback. Nothing to change in your app. Update `ai.graine:inapp-android` and `ai.graine:inapp-android-rtc` together.

## 0.10.2

- **Withdrawn the same day — use 0.10.3,** which redials after half a second.
- **A WebRTC call the server acknowledges but never answers is dialled again after 3 seconds.** The engine used to wait out the whole 12-second WebRTC attempt for such a call — a long *Connecting…*, then the call continued without WebRTC — because its 15-second answer ceiling could never fire inside that budget. Now, 3 s after the server's first reply with no answer, the stuck dial is cancelled and made once more on a fresh connection (what a second tap did by hand); a second stuck dial continues on the standard connection, with `transportFallbackReason` `no_answer`. Nothing to change in your app. Update `ai.graine:inapp-android` and `ai.graine:inapp-android-rtc` together.

## 0.10.1

- **The SDK registers for pushes itself: no `FirebaseMessagingService` to write.** With Firebase Cloud Messaging in the app (`google-services.json`, the Google services plugin and `com.google.firebase:firebase-messaging`), the SDK's own messaging service (`ai.graine.inapp.GraineMessagingService`, merged from its manifest) receives every new token and rings Graine's call pushes, leaving every other message alone; and once a process, when the SDK starts, it reads the current token, so an install whose token is older than this version registers too. A token the SDK already holds is not sent again. An app that turned Firebase's automatic token creation off is left to its choice. Firebase stays optional: the SDK is compiled against it and ships without it (no new dependency), an app without it builds — R8 included — and runs as before.
- **Already have your own `FirebaseMessagingService`?** Nothing changes: the SDK's is declared at priority -1, below yours, so yours keeps receiving every message and hands Graine's over with `GraineCalls.onNewToken(context, token)` and `GraineCalls.handlePush(context, data)`, as before. A debug build logs it when another messaging service receives the app's messages.
- `no_push_token` now says what is missing: Firebase Cloud Messaging not in the app, Firebase not set up (google-services.json or the plugin), automatic token creation turned off, or the reason Firebase gave no token — each with its fix.

Until a face arrives, and if it never does, the system font. `GraineConfig.fonts` is now optional; a family mapped there is drawn from the app's file and never fetched.

## 0.2.0

- The design the brand chooses in the dashboard is drawn. A component's own style still wins over the design. From a server that sends no design, everything looks exactly as before.

- `GraineConfig.fonts` maps the dashboard's font families to typefaces the app bundles; an unmapped family draws in the system font.
- `GraineInApp.design`, `themeTokens(context)` and `previewDesign(design)`, for an app drawing its own UI in the brand's design or previewing one.
